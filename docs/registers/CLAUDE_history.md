## Session 21 engineering discoveries (2026-05-06) — operational findings only

- **Pipeline order matters in idempotent zone management.** The order detect → upsert → recheck → expire is the only correct order: (a) detect produces new candidates; (b) upsert writes ACTIVE for new + leaves existing untouched; (c) recheck flips status based on price action across new + existing; (d) expire flips date-based across all. Reordering any step makes the sequence non-idempotent or produces wrong final state. Session 21 fixed TD-071 by moving expire from BEFORE detect (broken — expires existing zones using last cycle's data) to AFTER recheck. Codified as: **for any pipeline that detects + upserts + recheck-conditions + expires, the only correct order is detect → upsert → recheck → expire. Document this in the script's main() docstring**.

Default Task Scheduler settings disallow battery starts AND stop tasks when going on battery. For laptop-based production system, this drops cycles invisibly. Fix: `DisallowStartIfOnBatteries=$false` AND `StopIfGoingOnBatteries=$false` on every market-hours task. Codified as: **at task creation time, every NEW Task Scheduler task that runs during market hours MUST have battery flags disabled. Audit existing tasks regularly.** This is Rule 23's natural extension (Rule 23 = mirror v1 pattern; this is the explicit battery flag requirement).

- **PowerShell `copy /Y` doesn't work in PS environment.** Session 21 lost ~30 min on TD-070 v2 deploy because `copy /Y file.py file.py` (cmd.exe syntax) returned no error in PowerShell but produced a 0-byte truncated file. Fix: read file content, string-replace to insert before exit line, write back. ## Session 29 engineering discoveries (2026-05-14 firefighting + 2026-05-14→2026-05-16 build) — codified as B24 + B25 + B26 + B27 + B28 + operational findings

**Bug B24 (anti-pattern) — `.env` edits do not propagate to running processes.** Token files like `.env` are read at process startup. A long-running consumer (websocket feeder, daemon, cron'd script that doesn't auto-exit) holds whatever value was loaded at startup until killed. After any `.env` mutation, every consumer process that read the affected variable MUST be killed and restarted; verifying the on-disk value matches (e.g., `grep KEY .env`) is necessary but not sufficient. Today's 2026-05-14 incident: operator ran the token-refresh sequence twice with correct end-state in `.env`, but `ws_feed_zerodha.py` had loaded the prior day's token at 09:14 IST cron start and continued failing auth in a silent reconnect loop until manually killed 9 hours later. Symptom is operationally indistinguishable from "Step 2 of token refresh was skipped" — diagnostic discipline requires checking the running consumer's behavior (log tail), not just the on-disk state. Codified as: **`.env` changes require consumer restart, full stop. Filing rule for any new `.env`-mutation runbook: include a "Step Nd — Restart consumers" mandatory clause.**

**Bug B25 (anti-pattern) — TRUNCATE vs DELETE on bloated tables.** For Postgres tables under statement_timeout pressure, `DELETE FROM table WHERE ...` cannot be used to recover bloat — the DELETE itself is what's timing out. `TRUNCATE table` is the only operational primitive that works at scale because it is DDL (drops + recreates the underlying file atomically), runs in O(1) on table size, and resets indexes inline (no `REINDEX`, no `VACUUM FULL`). Constraint: TRUNCATE deletes ALL rows, so only safe for tables whose consumers all read fixed-window-recent data (the ephemeral-rolling-window pattern, e.g. `market_ticks` 10-min window). 2026-05-14: `market_ticks` 62 GB → 856 kB in <1s, with the feeder writing successfully on next batch. Codified as: **for any table whose retention horizon is shorter than its read-window-floor, TRUNCATE is the canonical recovery; DELETE is structurally unsafe.** Apply: design check at every new pg_cron retention job — if the worst-case DELETE workload could ever exceed statement_timeout, the design is wrong; reduce horizon and increase cadence instead.

**Bug B26 (anti-pattern) — `pg_cron` failures are invisible by default.** The `cron.job_run_details` table records every cron run, including failures, but no MERDIAN telemetry polls it. A retention or maintenance job can fail every weekday for weeks before any operator-visible symptom emerges (2026-05-14: `delete-old-market-ticks` failed 14+ consecutive weekdays before producing the 62 GB bloat that triggered Incident 1). Codified as: **any pg_cron job introduced to production must be accompanied by either (a) a polling check that surfaces failures within 24 hours (Telegram alert or dashboard widget), or (b) an explicit entry in the operator session-start checklist.** Filed as TD-NEW-B (S1) for the alerting-layer implementation. Workaround pre-implementation: include `SELECT jobname, status, return_message, start_time FROM cron.job_run_details WHERE start_time > now() - interval '7 days' AND status != 'succeeded'` in session-start gate.

**Bug B27 (anti-pattern) — Generate-series in PostgREST with `timezone()` cast of wall-clock IST strings produces phantom misses.** During 2026-05-14 spot-gap diagnosis: `SELECT generate_series(timezone('Asia/Kolkata','2026-05-14 09:15:00'), timezone('Asia/Kolkata','2026-05-14 15:29:00'), interval '1 minute')` actually generates `14:45 IST → 20:59 IST` (5h30m forward-shifted). The string `'2026-05-14 09:15:00'` is parsed as UTC by default; `timezone('Asia/Kolkata', utc_value)` then converts that UTC value to IST display, but the underlying timestamptz is unchanged. My query produced 245 "phantom missing minutes" in post-market hours, none of which were real. Codified as: **build expected-time series in UTC at actual UTC times** (e.g., `'2026-05-14 03:45:00+00'::timestamptz` for 09:15 IST trading-start) **and let the join handle TZ conversion in output formatting only.** Apply: any audit query that compares IST-window expectations against `bar_ts` storage should use this pattern; never use `timezone()` cast to construct an IST series from a wall-clock string literal.

**Bug B28 (anti-pattern) — Regex capture of arbitrary trailing tokens is unsafe in command-injection contexts.** v1 of `migrate_to_pythonw.ps1` used regex `(?<rest>(\s+\S+)*)\s*$` to capture trailing arguments after a `python script.py` invocation in a `.bat` file. The regex greedily captured shell redirection operators (`>>`, `2>&1`, etc.) which look like normal whitespace-separated tokens. These were then passed to `pythonw.exe` as command-line arguments, which would have caused silent crashes (pythonw treats `>>` as a script-file argument and fails to start, with no console visible). Codified as: **when capturing command-line arguments to pass to a different shell context, explicitly whitelist syntactically-meaningful argument shapes** (e.g., flags starting with `-`/`--`, `.py` files, quoted strings) **and explicitly blacklist shell metacharacters** (`>`, `>>`, `<`, `|`, `&`, `2>`, backticks). Apply: any code that re-emits captured tokens into a different execution context (cross-shell, cross-process) is in scope.

## Session 33 engineering discoveries (2026-05-22) — codified as ADR-011 + chain-table held-strike rebuild + retest cohort empirically validates ADR-009 §Phase 1

**Eight S33 operational findings:**

- **Source-table fitness-for-purpose is a category error class.** `hist_atm_option_bars_5m` was designed for wick-reversal analysis (read by `experiment_26_option_wick_reversal.py` and friends). `hist_option_bars_1m` is the actual vendor chain (54.8M rows, dense, paid-for). Codified as: **when a vendor table appears "sparse" for a use case, FIRST verify the table is the canonical source for that use case. Aggregated tables built for analysis X may be wrong source for use case Y even when both involve "options" data.** TD-S32-NEW-4 vendor cross-tier drift made architecturally moot by the rebuild — no longer reads the drifting column.

- **Experiments 1-50 made the inverse error.** `build_hist_pattern_signals_5m.py` joined `hist_atm_option_bars_5m` at signal time AND signal+30m WITHOUT same-strike enforcement — comparing premiums of two different vendor-picked strikes' and calling the % change "PnL". The "negative median everywhere" of ENH-100 v6 was the inverse error (mathematically correct held-strike check on the wrong source table). - **Per-tuple range-prefetch is the canonical pattern for chain reads.** Per-primitive query (19,399 × 6 horizons = 116k queries) hits HTTP/2 GOAWAY. Codified as: **for chain-table reads at scale, prefetch per (strike, expiry, option_type) tuple over a timestamp range, not per (primitive, horizon) point. ## Session 34 engineering discoveries (2026-05-24) — codified as ADR-012 + spot-anchored SL doctrine + universal big-move-day capture audit + selection-research arc framework

**Six S34 operational findings:**

- **Capture is not the binding constraint; selection is.** Universal audit of ≥1% intraday move-days across 2025-04-01 → 2026-05-19: 119 days qualified (NIFTY 57, SENSEX 62 at parity 1.0% threshold); 118/119 captured (99.2%) by MERDIAN's ICT primitive layer with direction-aligned + zone-interaction filters; one miss (NIFTY 2025-05-20 D DISPLACEMENT_DOWN existed but price didn't reach zone). Origin distribution: FVG 84% (BEAR 47%, BULL 36%), OB 16%; timeframe D+W 74% (D 47%, W 27%), H 14%, M5 11%. The system sees every move structurally. The bottleneck is selection — on any given morning 50+ active aligned zones exist across W/D/H/M5, and the system has no ranking layer to predict which fires today. Codified as: **capture and selection are distinct problems with distinct solutions. Capture-rate ≥99% indicates the structural foundation is sound. Selection-research is the next-layer build, not a capture-layer fix.**

- **The retest is structurally the moment of maximum local risk for an ICT trade.** S34 SL-variant backtest on 7 same-day retest entries: tightest spot-anchored SL (0.3% adverse 5m-close-through from entry) **never triggered on any of the 7**. The retest is the structurally invalidatable moment — price has come back to the zone and is at the decision point; once it has begun rejecting, it does not return through within the same-day window. This is consistent with ICT canon: the retest IS the entry-validation event. Codified as: **for ICT retest entries the SL anchor measures thesis failure (close-through zone invalidation on 5m), not microstructure noise. Once the retest survives the first 5-15 minutes, the trade is what it is — structural pricing.**

- **Premium SL on ATM held strikes is the wrong instrument-stop pairing.** S34 backtest: 5% intra-bar premium SL eliminated 100% of structurally-correct winners (0/7); 10% same (0/7); even 15% intra-bar only saved 3/7. 1m-close-through 5%/10% same pattern. ATM held strikes wick 5-15% in first 30-60 min from bid-ask + theta on tight DTE + IV crush as morning gamma compresses; the wick noise is uncorrelated with whether the structural thesis is intact. Wide premium SLs (Compendium-era 30%+) approximate the right intent indirectly but couple SL hit rate to volatility regime, expiry distance, and bid-ask conditions unrelated to structural premise. Codified as ADR-012: **SL must anchor to spot zone-invalidation on 5m-close-through. Premium-based stops on ATM options measure microstructure, not thesis. Wider premium stops are an indirect approximation; spot stops are the canonical anchor.**

- **Vendor-purchased data and self-ingested data sit in different tiers; transitions between them create silent coverage gaps in downstream consumers.** TD-S34-NEW-4: `hist_option_bars_1m` returned full chain on pre-2026-04-01 dates and zero rows on all nine probed post-Apr-2026 dates. Pre-Apr-2026 was vendor-purchased dense across the 12-month window paid for and verified. Post-Apr-2026 is MERDIAN-ingested via a different writer path. The framing "MERDIAN failed to ingest entirely" cannot be the full picture — plenty of full-ingestion days post-Apr-2026 are observed elsewhere in the system. Diagnostic path is tier-transition + ingest writer locate, not token-failure pattern-match. Codified as: **when a backfill cohort's coverage suddenly stops at a calendar boundary, the first diagnostic is "what tier of data lives on each side of the boundary?" — not "what failed?" The transition may be architectural (storage path mismatch) not operational (ingest failure).** Initial framing of TD-S34-NEW-4 as "Kite token expiry on MALPHA (TD-080-adjacent)" was incorrect and recorded as superseded per operator domain knowledge (S33 push-back pattern applies again).

- **Prior research stands; the ENH-108 gap expands the addressable cohort, not refutes findings.** When S34 cohort SQL surfaced only 7 same-day first-retests landing on ≥1% move-days (vs the implicit expectation of "much more"), there was a momentary alarm about whether prior retest-cohort research (D-FVG retest 78-86% WR, H-FVG retest 60-76% WR) was invalidated. The correct framing: prior research measured the *first-touch retest cohort*, which is thousands of events across the 14-month window; the 7 is a *subset* (first-touch retests that happened on a ≥1% move-day). The 111 other ≥1% move-days are powered by non-first-touch retests, invisible to `ict_primitive_outcomes` per ADR-004 §10's single-`first_retest_ts` schema — a real but bounded model gap (ENH-108 filed). ## Session 35 engineering discoveries (2026-05-25) — codified as ADR-012 IMPLEMENTED + ADR-013 PROPOSED + ENH-106 v8/v8.1/v8.2 dual-source chain reader + ENH-106-SL v9 spot-anchored SL writer extension + TD-S34-NEW-4 mechanical closure

**Nine S35 operational findings:**

- **A data-tier transition is a three-surface architectural concern, not one.** S35 started with v8 patch routing chain prices via 2026-04-01 boundary check (pre→`hist_option_bars_1m`, post→`historical_option_chain_snapshots`). Single-cell test produced `n_tuples=0` because `_enum_anchor` silently early-returned on `_nearest_weekly_expiry` returning None — the vendor expiry calendar `hist_atm_option_bars_5m` caps at 2026-04-02/04-07 and contains no expiries for a post-Apr retest day. v8.1 patch extended `_load_expiry_calendar` to UNION vendor + HOCS expiries. Then PostgREST 8s statement_timeout (57014) surfaced because the new HOCS expiry walk paginated 2.67M rows just to find 10 distinct values. v8.2 patch swapped pagination for `get_hocs_distinct_expiries(text)` RPC + `idx_hocs_symbol_expiry (symbol, expiry_date)` covering index for sub-100ms execution. ATM strike picking was already independent in v7 (manual via `STRIKE_INTERVAL` grid) — third surface pre-resolved. Codified as: **when a data-tier transition is identified, audit ALL surfaces that depend on the source table, not just the headline column. Each surface needs its own routing logic at the same boundary. Single-patch coverage is not closure; iterate through every consumer.**

- **DISTINCT-over-millions-of-rows must live in the DB, not in the client.** Initial v8.1 HOCS calendar walk used `sb.table("historical_option_chain_snapshots").select("expiry_date").eq("symbol", X).range(0, 999)` paginated to find ~10 distinct values across 1.3M-per-symbol rows. PostgREST round-trips alone = 1300 page fetches × ~100ms latency ≈ 2+ minute hang. The right shape is a Postgres function `STABLE LANGUAGE sql` returning `TABLE(expiry_date date)` with `SELECT DISTINCT ... ORDER BY ...` exposed as `sb.rpc("get_hocs_distinct_expiries", {...}).execute()`. With a `(symbol, expiry_date)` covering index, Index Only Scan + HashAggregate clears in 325ms. Codified as: **supabase-py REST has no DISTINCT primitive; any "find unique values for a key prefix" query over >100k rows MUST be a DB function via RPC, not a client-side paginated walk. The cost difference is 4 orders of magnitude.**

- **PostgREST 8s statement_timeout doesn't apply to direct DB connections.** Initial confusion when `EXPLAIN ANALYZE get_hocs_distinct_expiries('NIFTY')` returned 325ms in Supabase SQL editor (direct DB connection via postgres role) but timed out via PostgREST role connection from the script. PostgREST role has a configured 8s `statement_timeout`; direct DB role does not. This is also the same property exploited by `SET statement_timeout=0` for index builds on multi-million-row tables (S29 created `ix_hist_option_bars_1m_bar_ts_strike` this way; S35 created `idx_hocs_symbol_expiry` this way). Codified as: **PostgREST writes/reads share an 8s ceiling that does not bind direct DB sessions; long-running DDL or `EXPLAIN ANALYZE` always goes through Supabase SQL editor or psql, never the JS/Python SDK.**

- **`historical_option_chain_snapshots` is the post-Apr-2026 canonical chain history — and its schema is shaped differently from `hist_option_bars_1m`.** Tier-1 vendor table `hist_option_bars_1m` is keyed on `instrument_id` (uuid), uses `close` as the price column, and is 54.8M rows of vendor-purchased dense data through ~2026-04-01. ## Session 69 engineering discoveries (2026-08-12/13) — codified as ADR-021 + ADR-022 + the read-path freshness corollary

**One symptom, five causes, mostly unrelated.** The operator reported "no pin/accel zones on TradingView for days." That thread produced: a disk-full cascade, a view that had been slowly outgrowing its statement timeout since May, a Pine render bug that only manifests at one timeframe, a detector frozen for 53 trading days, and a live SEBI market-structure change nobody had noticed. **Four of the five were pre-existing and independent of each other**; the 08-12 disk incident merely made the pile visible. The lesson is not "look harder" — it is that a single reported symptom is a sampling of the failure surface, not a description of it. Stop root-causing at the first sufficient explanation.

**The failure that reports nothing is the expensive one.** Every defect found this session had the same signature: **the system said it was fine.** `eod_health_check.py` returned `[OK]`. The GEX writer was healthy and `gex_strike_snapshots` was fresh. `MERDIAN_ICT_EOD` reported `State: Ready`, `LastTaskResult: 0`. The Pine generator ran and produced an overlay. None of that was false; all of it was irrelevant. **Writer-state and read-path-state are independent facts, and a health check that only knows the first is a green light over a dark road.**

**Cost growth is arithmetic, and it is a design-time property.** The pin/accel views were correct on the day they shipped and correct on the day they broke. Nothing changed except the row count — 45K → 1.06M over 250+ sessions — and a recursive CTE over an unscoped base table has a cost curve you can write down in advance. The failure crossed the PostgREST 8s ceiling on no particular day, which is exactly why nothing caught it. **When a view's only consumer reads one row, the scoping belongs inside the view.** Raising the timeout would have bought months and re-armed the same trap at a larger N.

**Fixing the slow thing can create the silent thing.** The ADR-021 scoping made `fetch_positioning_landscape` fast. Before it, a stalled GEX writer produced a `57014` — loud, and unmissable. After it, that same stall produces stale pin/accel zones returned instantly: plausible, fast, wrong. The speed fix *converted a loud failure into a quiet one*, and the only reason that is not now shipped is that S69 noticed and filed it. **Every latency fix on a read path must ship with its recency floor in the same pass** (ADR-018 D2).

**Two defects on one job, and repairing the loud one alone would have shipped the quiet one.** The M5 detector is frozen because `OB_MIN_MOVE_PCT = 0.40%` cannot be reached (30-session maxima 0.366% / 0.369%). That is the obvious fix, and it is a trap: the job also fires at 15:35, which since 2026-08-03 is **inside** the CAS auction / extended-derivatives window. Recalibrate the threshold without re-timing the job and the detector resumes — writing zones off auction-contaminated bars, confidently. **Enumerate every defect on a broken job before repairing any of them; the repair order is a correctness property, not a preference.**

**MERDIAN can be wrong about the market without being wrong about anything it can see.** CAS is the deepest finding of the session and the one the system had no possible way to surface. The pipeline kept executing correctly against a market that had moved underneath it: continuous trading for F&O names ends at 15:15 now, the close is an auction equilibrium published 15:30–15:35, and the index derivatives MERDIAN actually trades run to 15:40. **Rule 18 said `trading_calendar` is an external trust-anchor that must be validated against the official NSE source. S69 is the same lesson one level up: session *timings* are as much a trust-anchor as session *dates*** — and they change by circular, not by error.

**Two independent causes of one symptom, and the second was found by accident.** Thin daily intraday structure had a sufficient explanation all session — the M5 detector frozen since 06-02. It was true, and it was not the whole story. A `git status` at close surfaced an uncommitted `# S69-C1-DAILY-HISTORY` edit: `DAILY_LOOKBACK = 60` had been sitting in `build_ict_htf_zones.py` defined and never referenced, so the daily OB/FVG layer evaluated **one** prior session while the weekly layer walked 52 weeks. **Sufficient is not the same as complete**, and the discipline that catches this is bounding the symptom rather than explaining it. **A correction worth more than a fix.** "MALPHA Zerodha auto-refresh is failing" had been carried as a live priority item. It was never a mechanism. The operator rotates the token by hand every morning; the 08-12 "dead token" was `.env` corruption from a `sed -i` on a full disk, where the unquoted `<` in the placeholder additionally broke every subsequent source of the file. **A carry item that names a component can survive many sessions without anyone checking the component exists.**

- **A read path made fast must be made fresh in the same pass (S70, ADR-023).** ADR-021's scoping fix took the pin/accel views from `57014` timeouts to instant returns — and converted a **loud** failure into a **quiet** one: a stalled GEX writer now returns week-old zones in milliseconds, plausibly rendered, with nothing saying so. Staleness goes in the artefact the operator sees, not only in a log.
- **The CAS settled close is retrievable, and it lands in the 15:29 IST bar (S70, ADR-022 D2 ANSWERED).** Dhan `/charts/intraday` across the auction: 15:06–15:14 real OHLC; **15:15–15:28 the index frozen at the 15:14 value with that bar's volume carried forward**; 15:29 carries the settled close. - **CAS auctions the constituents, not the index (S70).** NIFTY and SENSEX are **computed** from Category-I stocks, so while those stocks are in the auction the index has no continuous input and simply repeats its last value, then recomputes in one step when equilibrium prices publish. - **`close == open` means settled-at-the-same-price, not unsettled (S70).** `capture_cas_close.py` Guard 3 was built from **two hand-picked samples** where the settled price happened to move, and it rejected 10 of 28 symbol-days whose flat bars already held the **correct** close. **A guard built from N=2 is a guess wearing an assertion's authority.** Cross-check against an authority; do not infer settlement from movement.
- **A defensive fallback chain does not make a system robust — it makes failure quieter (S70).** `load_vix_history_rows()` tries three tables, swallows exceptions with `continue`, keeps the longest, and **logs nothing**. Two are empty, the third frozen since 2026-03-11, and `vix_percentile` has been scored against a five-month-old distribution with everything downstream reporting success. **A source-selection function must record which source answered and how many rows it returned.** The logging defect was filed *above* the missing writer: the mechanism outranks the instance.
- **A first→last range check cannot see a truncated tail (S70).** `eod_health_check.py` returned `[OK]` on a session missing 15:16–15:29, because the 16:00 postmarket capture extends the endpoint past the gap and ~362 of ~375 bars sat inside tolerance. Freshness and endpoints both looked fine while the most consequential minutes were absent. Health checks need a **continuity assertion** — expected bars per symbol per session — not only freshness.
- **Read your own record before reasoning about it (S70).** The Zerodha propagation gap was diagnosed, designed and filed as **TD-NEW-7 (S1) on 2026-05-13**, precursor "C-10" dating to **Session 7**, with two prior outages already recorded. The register held the answer for ~40 sessions.
- **A committed doc-close is not a completed doc-close (S70).** The S69 twelve-file close was committed and tagged but **never re-uploaded to project knowledge**; at S70 open PK still held the pre-S69 baseline (CLAUDE.md 1,019L vs 1,054L on disk). Byte-level baseline verification at session open is what caught it.
- **`NO_DATA` is not a valid `script_execution_log` exit reason (S70).** It is absent from `chk_exit_reason_valid`, so the row is rejected and the run lands as **CRASH** — which is why 14 benign auction-window skips a day looked like failures. Valid set: SUCCESS / HOLIDAY_GATE / OFF_HOURS / TOKEN_EXPIRED / DATA_ERROR / SKIPPED_NO_INPUT / DEPENDENCY_MISSING / CRASH / TIMEOUT / RUNNING / DRY_RUN.
- **Never auto-correct a mismatch between two sources (S70).** `backfill_cas_close_from_daily.py` classifies MATCH / MISSING / MISMATCH and writes only MISSING. A disagreement means one source is wrong; overwriting one with the other destroys the evidence needed to determine which. Report, leave alone, decide deliberately.

**6. ## Session 70 engineering discoveries (2026-08-22) — codified as ADR-023 + the ADR-022 D2 answer

**The data was one minute outside the window.** For 14 trading days MERDIAN closed every session on a stale price, and the correct one was sitting in the very next bar of an endpoint it was already calling. The `*/1 …09` cron's last run at 09:59 UTC requests the 15:28 bar; the settled close lands in 15:29. Not a vendor limitation, not a CAS consequence, not missing data — **an off-by-one at the boundary of a capture window that nobody had re-derived after the market's closing mechanics changed underneath it.** The lesson is not about cron syntax. It is that when an external boundary moves, every window defined relative to the old boundary is silently wrong, and the wrongness is invisible precisely because each window still does exactly what it was written to do.

**Two guards, both built from two samples, both wrong in the same way.** Guard 3 in `capture_cas_close.py` tested `close != open` as a proxy for "settled", inferred from two sessions where the settled price happened to move. The `OB_MIN_MOVE_PCT` finding measured single-bar bodies against a threshold defined over five bars. Different code, different session, same failure: **a quantity that was easy to measure stood in for the quantity that mattered, and the substitution went unstated.** Guard 3 rejected 10 correct closes; the threshold measurement nearly justified a recalibration that would have invalidated the Exp-15 cohort. Both were caught only because an independent authority existed to check against — the daily endpoint in one case, the HTF zone rebuild in the other. **Where no independent authority exists, this class of error is undetectable.**

**Every concealment mechanism found this session was a helpfulness feature.** The fallback chain in `load_vix_history_rows()` exists so a missing table does not break the run — and it hid five months of staleness. The range check in `eod_health_check.py` exists so a session with a few missing bars does not alarm — and it reported `[OK]` on a session missing its close. `is_filler_bar()` exists to refuse synthetic bars — and it correctly refused nothing, because the auction plateau carries real volume. **None of these are bugs. Each does exactly what it was designed to do, and each converts a loud failure into a quiet one.** The pattern to watch for is not broken code; it is defensive code without observability. A `continue` that swallows an exception must log what it swallowed.

**ADR-021 made something better and something worse in the same commit.** The scoping fix was correct — 1.06M rows to ~80, output byte-identical. It also removed the only mechanism by which a stalled GEX writer announced itself. S69 saw this immediately, wrote it down, filed TD-S69-NEW-3, and left the exposure live for two sessions. **Seeing a problem and filing a problem are not the same as fixing a problem**, and the register is where correct observations go to wait. ADR-023 exists to make the floor part of the change rather than a note about the change.

**The answer had been in the register since May.** TD-NEW-7 — the Zerodha propagation gap — was diagnosed at S28 with the fix fully designed, carried as S1 through roughly forty sessions, and produced its third outage on 08-18. At S70 it was re-derived from scratch: a web search on token expiry, a `grep` on the box, a hypothesis about a flush window that live evidence then falsified. `project_knowledge_search` was available throughout and was not called once. **The most expensive failure of the session was not a defect in MERDIAN. It was reasoning about MERDIAN's history without reading it** — the same shape as D.27.9's "stop root-causing at the first sufficient explanation," one level up: bound the problem against the record before explaining it.

**And the record itself had quietly forked.** The S69 doc-close was committed, tagged, and pushed to three environments — and never re-uploaded to project knowledge, so the next session opened against a two-commit-stale baseline. It was caught by a byte-level hash check at session open, not by anything in the process. **Git and project knowledge are two stores of the same truth, and only one of them is what the next session actually reads.** Rule 3's final line — re-upload to project knowledge — turns out to be the load-bearing one.
