# Data access: vendors, timezones and source tables

Relocated verbatim from `CLAUDE.md` at Session 86 (ADR-028). Rule text is
unchanged; only its location moved.

- ❌ Annotating `option_chain_snapshots.raw`. It is the vendor payload verbatim, and that is its only property. Derived flags go in their own columns, or are computed at read time from `ts`. (Session 71.)
- ❌ Setting `page_size > 1000` in Supabase pagination — Supabase hard-caps at 1000 rows per request regardless. Use `page_size = 1000` and loop. (Session 11 bug B2 / Rule 15.)
- ❌ Using `astimezone(IST)` on `hist_spot_bars_5m.bar_ts` — bar_ts is stored as IST labeled +00:00. Converting timezone adds 5:30 and shifts all bars out of market hours. Use `replace(tzinfo=None)` instead. (Session 11 bug B3 / Rule 16.) **NOTE: This is era-conditional. Pre-04-07 use `replace(tzinfo=None)`; post-04-07 use `astimezone(IST)`. See Rule 20 (Session 15) for era-aware helper.**
- ❌ Using `ret_30m` from `hist_pattern_signals` as a decimal fraction — it is stored as percentage points. Divide by 100 first. (Session 11 Rule 14.)
- ❌ Trusting the dashboard EXIT AT label for trade exit timing — the label slices the UTC timestamp string directly (`exit_ts[11:16]`), not the IST-converted version. On a 09:31 IST signal this shows 04:31, not 10:01. Compute exit time manually: signal IST + 30 minutes. (TD-038, Session 11 extension.)
- ❌ Querying `market_spot_session_markers` for `open_0915` or `gap_open_pct` — the live column is `open_0915_ts`, not `open_0915`. Derive open price from `market_spot_snapshots` first tick in OPEN window. Derive gap from `hist_spot_bars_5m` prev_close. (Session 13 Rule 17.)
- ✅ **`ltp` is the last trade, not a price.** On expiry morning, far-ITM SENSEX puts printed ~40 points **below intrinsic** — not an executable quote, just a stale print on a thin strike, while the liquid call side showed normal extrinsic. Anything computing extrinsic, moneyness, or synthetic spot from `ltp` inherits a silently negative value biased toward the least liquid strikes. **Use `bid`/`ask` where the quantity must be executable.**
- ✅ **A service whose normal shutdown is `failed` cannot be health-checked by its state.** `merdian-wsfeed` catches SIGTERM, so every trading day ends in SIGKILL and `Result: timeout`. A hang and a clean stop are indistinguishable to `systemctl is-active` — which produced one false alarm and left one real outage detectable only by reading the journal. **If the healthy path and the broken path share a terminal state, the state is not a signal.**
- ✅ **Alerting that fires and is not read is a delivery problem, not an instrumentation gap.** The 08-18 outage was recorded three times in `ws_feed_zerodha.log`, alerted three times through `wsfeed_alert.sh`, and triggered `OnFailure=`. S70 still called it unreconstructable, because nobody opened that file. **Before adding instrumentation, check whether the existing signal was emitted and ignored.**
- ✅ **Never propose removing infrastructure before enumerating what depends on it.** `snapd` was 1.3 G and looked like dead weight on a headless box. `amazon-ssm-agent` is a snap — the sole access path — and `certbot` holds the Marketview TLS renewal. **`snap list` was the first command, not the confirmation step.**
- ✅ **`git status` clean ≠ file tracked.** A `.gitignore` pattern (`*.txt` at line 44) silently swallowed a committed-by-intent manifest with **no untracked listing at all**. `git check-ignore -v <path>` is the only tell. Fix with a negation rule, not `git add -f` — the force flag hides the problem for the next file. (S68, `d3b02bb`)
- ✅ OpenItems Register closed (2026-04-15)
- ✅ **F1 (ICT zone time_zone classification) SHIPPED** (2026-04-27, Session 10) — `fix_ict_time_zone_utc.py` converted UTC→IST before time-bucket assignment. Verified live.
- **Monitors must not share the failure chain of what they watch (S53):** all four S52 monitors used the same `source .env` prefix as the capture layer and died with it (watchdog + patient together), so the blackout was invisible — the watchdogs were dead too. Monitor env-loading must be independent of the chain it monitors.
- **Upserts can mask per-symbol write loss (S54):** the volatility insert→upsert(on_conflict=symbol,ts) correctly stopped 409 crashes but converted SENSEX's lost/repeated writes from a loud failure into a silent merge — SENSEX compute silently under-writes ~½ of cycles (TD-S54-NEW-1). After any insert→upsert change, audit per-symbol distinct-ts coverage to confirm writes aren't being merged away.
- ✅ **Pre-existing-table discovery discipline; `hist_gamma_metrics` is the canonical historical gamma series** (Session 62, 2026-07-01) — Always check for an existing table before CREATE. A full-window (Apr 2025–Mar 2026) both-symbol 1-minute `hist_gamma_metrics` series already existed (net_gex/flip_level/regime populated) with its ONE gap being an empty `gamma_concentration` column — so the task collapsed from "recompute everything" to "fill one column." Hard-won facts about it: **net_gex is stored UNSCALED** (×1e7 vs live's /1e7 Cr; median ratio ~1.007e7); its `bar_ts` is **IST-clock-as-UTC at `:59`** (live `ts` is real UTC at `:00`; shift = −5h30m + truncate-to-minute); `gamma_concentration = max|gex|/sum|gex|` (Herfindahl dominance ratio, **scale-invariant** — so the 1e7 convention is moot for the fill). This table (post-S62) is the canonical historical gamma series for both symbols, full-window, and the substrate for the ENH-116 expiry-memory seed.
- ✅ **iv is the master key — lean sidecar schema is correct** (Session 62, 2026-07-01) — In the historical per-strike Greeks sidecar (`hist_option_greeks_1m`), storing only `iv`+`gamma` costs nothing: every Greek recomputes from iv+S+K+T+r, and concentration is scale-invariant and needs only gamma. Dropping iv would have been the real mistake. Vendor `hist_option_bars_1m` is never mutated; the sidecar is additive.
- ✅ **"Correct-and-slower beats fast-and-subtly-wrong" — abandon divergent optimizations, never loosen the gate** (Session 62, 2026-07-01) — A `--fast` day-batched concentration path failed `--verify` (max |diff| 0.0754) with a residual divergence that six diagnostic rounds could not isolate (gamma/oi/strikes/expiry all measured bit-identical; the probe's own reconstruction had a bug). It was ABANDONED as dead code behind `--fast`, NOT loosened to pass. Same discipline held on the 2025-11-25 expiry case (skipped, not floored). A `--verify` divergence means the approach is wrong, not the threshold.
- ✅ **Cross-engine (StockMojo) parity isolates bugs** (Session 62, 2026-07-01) — Where two independent GEX engines agree, the structure is real; where they diverge, the divergence pinpoints the bug and its trigger. On the SENSEX flip bug (TD-S62-NEW), StockMojo matched MERDIAN exactly on regime, accel zone, amplify strike, and walls — the flip was the sole outlier, which is what confirmed it as a MERDIAN `compute_flip_level` bug (spurious deep-tail crossing under a NEGATIVE_γ near-spot short-γ pit) rather than a data/chain issue. Use cross-engine parity as a validator; treat the single divergent field as the diagnosis.
- ✅ **`ast.parse` alone does not prove a Python edit is safe — a `str_replace` insertion can silently eat a `def` header and leave an orphaned body that parses clean and NameErrors only at runtime (Session 64, `1be5239`→`61df758`).** The Phase-B helper insertion swallowed the `def compile_symbol(...)` header; `ast.parse` passed on the orphaned body, and the break surfaced only when the compiler ran. Rule (already canon, re-instanced here as a live case): every `str_replace` to a Python file is validated with `ast.parse` **and** `py_compile` **and** a named-function-existence check — the bare parse is insufficient. Codified as the S64 instance of the canon-v3 edit gate.
- ✅ **Marketview graduated from an internal `http://13.63.27.85/marketview` IP page to a public, TLS-terminated, Google-auth-gated app at `https://marketview.meridianalpha.in` (Session 64).** GoDaddy A-record `marketview` → `13.63.27.85`; TCP 443 opened on the SG *attached* to `i-0878c118835386ec2` (confirm the attachment via IMDSv2 first — this box has burned hours on orphan `launch-wizard-*` SGs, per S39); certbot Let’s-Encrypt cert + http→https redirect; oauth2-proxy (Google provider) in front of nginx with an `authenticated_emails_file` allow-list (`/etc/oauth2-proxy-emails.txt`). The load-bearing lesson: **`auth_request` must sit at server level on the *serving* 443 block, and the gate is only proven by a cross-browser no-session test — not by `nginx -t` or a reload.** The patcher twice scattered `auth_request` into an orphan certbot `return 404` block, leaving the serving block ungated; the reload succeeded both times and the site let everyone in. Server-level auth covers `/`, `= /index.html` (an exact-match location that would *not* inherit a `location /` gate), and assets together, with `/oauth2/` exempted. Codified in Deployment Topology §S64.
- ✅ **The EOD coverage guard's denominator is the active-universe / latest-EOD-date ticker count (~1,159), not the nominal ~1,385 universe; staleness is measured off the last *trading* day with a ~3-day Dhan-lag tolerance (Session 65, TD-S65-NEW-1).** `check_eod_coverage_freshness.py` was mis-tuned against the nominal 1,385 universe over a 5-day window, which produced a `/1` false-OK. `COMPLETE_EOD_THRESHOLD_PCT=95` is correct because it measures against the *active* universe (~1,159, the DMA layer rebuilt clean at 100% of active to 07-02). The guard is display-not-gate — the ingest is correct; only the freshness check needs the grounded 1,159 / last-trading-day / ~3-day-tolerance values.
- ✅ **OAuth credential rotation via a *new* Google client changes BOTH `client_id` and `client_secret` — and the exposure closes only when the OLD client is deleted, not when the new one goes live (Session 65, ENH-117 security fold).** The `client_secret` leaked in the S64 nginx-config dump was rotated by creating a new OAuth client (which changes both fields); update both lines in `/etc/oauth2-proxy.cfg` (leave `provider`/`redirect_url`/`cookie_secret`/`authenticated_emails_file`), set the redirect URI to `https://marketview.meridianalpha.in/oauth2/callback` char-for-char, clear JS origins (server-side flow), restart `oauth2-proxy` (→ `active (running)`), then verify login, delete the old client, and run the non-allow-list denial test. Rotation applied this session; the delete + denial-test closeout is the carry.
- **A builder gated on a coverage threshold inside a cursored-ingest loop must treat the gate-miss as non-fatal, not a loop-stop (S67, `f5b9afd`).** `run_equity_eod_until_done.py` drained the universe 50 tickers/lap but the DMA builder checks a 95%-of-universe gate every lap; on early laps the day is under 95%, the builder raises rc=1 by design, and stopping the loop on that rc strands the sweep permanently. Fix: builder rc!=0 logs-and-continues; only ingest failure / cursor==0 end the loop. The builder succeeds idempotently on the lap the day crosses 95%. Generalizes: a downstream consumer's "not ready yet" signal must not terminate the upstream producer's progress loop.
- **The active equity universe is 1,385 (dhan_scrip_map is_active + dhan_security_id not null); the true EOD coverage ceiling is 97.83%, not 100% or ~1,159 (S67).** ~28 permanent DH-905 dead security_ids + 2 no-history tickers cap coverage structurally. A freshness/coverage guard's denominator must be this active-universe count (what the builder *tries* to cover), not a trailing-window peak (~1,159, which excludes the DH-905 tail and moves with the numerator → false-OK). `check_eod_coverage_freshness.py` re-anchored to `_active_universe_count()`; min-coverage floor set to 92 (below the 97.83% real ceiling, above any genuinely-partial day).
- **`trading_calendar` is the system-wide holiday trust-anchor; it was wrong for ~3 months and silently defeated every gate (S60, TD-S60-NEW-2).** `trading_calendar.json` held 2 of 15 NSE-2026 equity holidays (Good Friday even misdated 04-18 vs 04-03), so the table read `is_open=true` on every holiday since ~April; the proven marker-writer gate trusted it and passed on Muharram, running the full compute chain on a closed market. Verbatim C-09/ADR-001 at the trust-anchor level. Fixed at source (15 official holidays, commit `bafddc2`, reseeded + stale rows flipped closed). Lesson: a gate is only as correct as its calendar — validate the calendar against the official NSE source before trusting any gate.
- **The canonical holiday gate is `core/trading_calendar_gate.py` — self-sufficient, fail-open; import it, never roll a new inline copy (S60, TD-S60-NEW-3).** It calls `load_dotenv()` itself + raw `requests` + `os.getenv`, deliberately bypassing `core.config.get_settings()`/`SupabaseClient` (which hardcodes a Windows `BASE_DIR` and finds no `.env` on AWS — TD-S60-NEW-5 — so a SupabaseClient-routed gate would silently fail-open every day, a no-op gate). The orchestrator is cut over to it (`38a82ff`); ~28 other bespoke gates migrate incrementally.
- **ENH-07 A has no live blast radius — the live gamma engine reads VENDOR (Dhan) Greeks; there is no live BS solver and no live risk-free-rate parameter (S61).** The risk-free rate only matters inside the historical Greeks backfill (TD-S58-NEW-1 / TD-095). `core/bs_engine.py` was built + validated (S=25218, K=24000, P=18, T=8/365, r=6.5% → IV=21.45%, γ=0.000134) as that backfill's substrate; ENH-07 A stays a historical/shadow track, not a live-writer change. Codified: don't chase a "live 6.5% rate" — there isn't one; the rate is a backfill parameter.
- **Both `hist_future_bars_1m` and `hist_spot_bars_1m` store IST-clock-as-UTC and pair with ZERO shift (S61, TD-S61-NEW-2).** The assumed −5h30m futures→spot shift was wrong: a UTC-forced diagnostic showed both tables carry hours 9–15 (IST clock mislabeled UTC) and are mutually consistent, so the −5h30m shift dropped 86% of pairs (14% yield) where zero-shift restores ~99%. Refines the TD-087 −5h30m note for the bar-pairing case. Verify the actual clock of BOTH sides before applying any offset.
- **Diagnose by running the failing call, not by inferring — and verify column/table names against live schema before querying (S66).** The S66 breadth-freeze diagnosis walked down SIX wrong theories (separate-chain / lap-timing / cursor-writeback / expired-token / clobber-race / wrong-URL), each killed by the next query; one real POST to the failing endpoint would have collapsed the tree turns earlier. The session ended on a hallucinated `equity_eod.trade_date` column (does not exist) — pull `information_schema` before writing SQL against an unfamiliar table.
- **Retention is OFF by operator ruling and the only thing holding it off is an assertion nobody automated — `jobid 19 active = false` is a TRIPWIRE to be checked at each SQL-editor doc-close (S89, `rulings_s89.md` #13 context).** The deleter is `pg_cron jobid 19`, `30 12 * * *`, `select public.cleanup_gamma_engine_daily()` — **note the name: the live job is `..._daily`, and ten live docs read `..._data` until S89 corrected the four that are not frozen archives.** Measured S89 in the SQL editor: `active = false`, last run 2026-09-08 12:30 UTC succeeded. **`merdian_ro` cannot read `cron.job`, so this check CANNOT be delegated to `bin/roq.sh`** — it belongs to the editor under postgres, and a `roq.sh` zero from that relation would be the reader, not the state (TD-S81-NEW-16 shape). The second line of defence is the S89 read-only export of the replay weeks (8 trading days 2026-09-22…10-01, both symbols, `option_chain_snapshots` + `gamma_metrics`, 32 files / 1,106,285 rows, `scratch/s89_export/manifest.tsv` sha `5f25f7f6…`, untracked): if the job is ever re-enabled, that window survives it. **The export is a shield, not a backup** — it is one window, it is untracked, and it does not make re-enabling safe.
- **A day can pass every density check and still be a frozen book — assert spot VARIANCE, not row counts (S89, TD-S89-NEW-1).** 2026-10-02 carried ~143k `option_chain_snapshots` rows across 83 distinct `ts` at the native 5-minute cadence, and `distinct_spot_values = 1` for both symbols (NIFTY 22421.95, SENSEX 71909.7, `spot_range 0.00`) — the previous session's 16:00:04 post-close prints, re-recorded 83 times on a closed day absent from `trading_calendar`. **Row count, `ts` count and cadence were all nominal.** `gamma_metrics` was correctly empty, so the gamma gate held while the ingest gate fail-opened. Before trusting any day for replay or a base rate, check that spot actually moved.
- **Per-symbol and pooled density are different numbers, and mixing them manufactures a defect (S89).** The retention/replay density target of "172 distinct `ts`/day" and the "thinned = 2" exclusion threshold are both **pooled across both symbols**: 172 ≈ 86 + 86, and 2 is 1 per symbol. Measured per symbol the native density is **74–87 distinct `ts`/day** at a true 5-minute cadence (modal gap 4.99–5.01 min on all nine days of the window). A per-symbol measurement checked against a pooled target flags **every** day as thinned. State which of the two a figure is before comparing anything to it.
- **`option_chain_snapshots.ts` is a true `timestamptz` — Rule 16 / TD-029's IST-as-UTC zero-shift is SPECIFIC to `hist_spot_bars_5m` and must not be assumed table-wide (S89).** Verified S89: raw `03:10:06+00` renders as **08:40:06 IST**, real session hours; had it been IST mislabelled as UTC, conversion would have pushed the session to ~14:45–21:10. **Use `AT TIME ZONE 'Asia/Kolkata'` on this table, never `replace(tzinfo=None)`.** The storage convention differs per table and has now bitten three ways — `hist_spot_bars_5m` (Rule 16), `hist_future_bars_1m` / `hist_spot_bars_1m` (S61, zero-shift pairing), and this one, which is simply correct. **Verify the actual clock of the specific table before applying or omitting any offset.**
- **`bin/roq.sh` is `psql` and streams — there is NO 1000-row cap, and Rule 15 (`page_size = 1000`) binds the PostgREST / Supabase-client path only (S89).** The real bound on this path is the **30 s `statement_timeout`**: an 85k-row day of `option_chain_snapshots` exports in **≈10.5 s**, well inside it. **Do not paginate `roq.sh` reads** — chunking an 85k-row day into 1000-row pages means 85 round trips for no correctness gain, and the per-connection cost (~2.7 s) dominates, so batching many statements into ONE invocation is the optimisation, not splitting one into many. When a read genuinely is too large, bound it by `ts` range or by day, not by row count.
