# Engine-stream ruling S105: `tape_w`, the live tape writer role (2026-11-10)

Status: **APPROVED by the tape stream (MR-OFL5) 2026-11-10 ~08:49 IST. NOT APPLIED.** Applied only when the operator runs the final apply block and the engine stream records the read-back here.

## Rulings
1. **Role `tape_w`** (display-only live writer). service_role stays off the tape box. LOGIN, NOINHERIT, NOBYPASSRLS, NOSUPERUSER, no createdb/createrole/replication, CONNECTION LIMIT 2, `statement_timeout 15s`, `idle_in_transaction_session_timeout 10s`, VALID UNTIL 2027-12-10 16:00 IST. Never granted to `authenticator` (no PostgREST/JWT path); direct pooler session only.
2. **Grants by command.** USAGE on `public`; `tape_live_cycle`, `tape_live_events`, `tape_live_wall`: SELECT, INSERT, UPDATE; `tape_live_label`: INSERT only. No DELETE/TRUNCATE/REFERENCES/TRIGGER/MAINTAIN, no sequences, no functions.
3. **RLS, today only.** `tape_w_select/insert/update` on the three upsert tables and `tape_w_insert` on `tape_live_label`, all scoped `trading_day = (now() AT TIME ZONE 'Asia/Kolkata')::date`. A leaked credential cannot read or rewrite other days through `tape_w`.
4. **Epoch rule (tape stream).** `live_run_id` is a per-symbol rebuild epoch; no key contains it; no DELETE is granted; readers keep only the newest epoch per (trading_day, symbol) for cycle/events/wall; labels are first-wins and exempt.
5. **Conflict targets** (from the 2026-11-10 constraint read): cycle -> `tape_live_cycle_pk (symbol, trading_day, instrument_token, ts_ist)`; events -> `tape_live_events_grain_uq` (NULLS NOT DISTINCT; **no PK exists on `tape_live_events`**, register item); wall -> `tape_live_wall_pk`; label -> `ON CONFLICT DO NOTHING` (no target, no RETURNING). `tape_live_cycle_grain_uq` is a second unique rule: a violation (token remap) is a counted, reported condition in the writer, never a crash. `tape_live_label.wall` is lowercase `call`/`put` (CHECK).
6. **Deliberate split from G-1.r (1).** G-1.r (1) ties the `data_contracts` update to the grant step for SELECT-only grants. For this write grant the contract rows are applied on the **writer-start day, after the first cycle has rows for both symbols**, because the contract checker reads a 5-minute product with no rows as MISSING (precedent: `gex_cycle_history` before it was populated) and would raise false alerts from 09:15. The `gex_cycle_history` writer-text UPDATE has no such effect and goes with the grant. After the INSERT, `cycle_health` for the new products is read and the `expected_per_cycle` ceilings are tightened.
7. **Password method.** Generated on the production box as the runner OS user (`tapelive`), `umask 077`, written straight into `/etc/tape-live/tape-w.env` (mode 600). Only a SCRAM-SHA-256 verifier is printed; the operator applies `ALTER ROLE tape_w PASSWORD '<verifier>'`. No plaintext in chat, the SQL editor, history, repo, /tmp or logs. Proof: a real login as `tape_w` through the pooler from the box. Rotation: same method, after 15:40 IST with the writer stopped; every 12 months, on any exposure, or on any box/OS-user/credential-file change; a Sydney-to-Mumbai move re-issues the DSN.
8. **Stage 2a** (moved to Thu 2026-11-12 08:50 IST) is file-only and holds no write credential: `/etc/tape-live/tape-live.env` carries only `TAPE_LIVE_RO_DSN` (a copy of the `merdian_ro` credential; same-credential caveats and joint rotation recorded). Stage 2b needs V1-V5 and the login proof to pass.
9. **R-2 (2026-11-12 ~04:30 IST): `merdian_ro` gets `default_transaction_read_only = on`** (role setting; engine-stream under G-1.r). Trigger: the tape runner's start-up guard refused `merdian_ro` (`default_transaction_read_only=off`, write-privilege on `gex_strike_snapshots` = f). Basis: `merdian_ro` holds no INSERT/UPDATE/DELETE/TRUNCATE/REFERENCES/TRIGGER on any `public` relation (S81.3: 0 of 233; S81.4 schema-wide REVOKE + default privileges revoked), so the setting removes no write that exists today; what it adds is that a session of that role rejects DDL (including `CREATE TEMP TABLE`), TRUNCATE, COMMENT/GRANT/REVOKE and sequence writes unless it overrides the default itself. It is a guard, not a boundary (the role can `SET` it back off); the boundary is the privilege state. `bin/roq.sh` already re-issues read-only as a SQL prelude, so documented consumers see no change. Evidence step before applying: `pg_stat_statements` for statements run by `merdian_ro`. Standing check (TD-S81-NEW-3): `merdian_ro` rolconfig now expects `default_transaction_read_only=on`. Caveat: `ALTER ROLE ... SET` applies at backend start; a pooled backend that predates it can still report `off` (see apply notes).
